# edge-tui

Edge 内核驱动的终端浏览器。用 CDP 控制 headless Edge，**把 DOM 里的文字提取出来，
用终端原生字符排版**；图片降级成低分辨率字符画占位，**二维码则按模块矩阵
1:1 无损映射 —— 在终端里也能用手机真扫出来**。

结果就是 w3m / lynx 那种**真·文字浏览器**：文字 100% 清晰、可读、能选中，
同时图片仍然以字符画形式占位可见。零 native 依赖，只靠 Node 内置能力 +
`pngjs`（二维码回归测试另需 `jsqr` / `qrcode`，均为 devDependencies）。

界面风格参考 [CodeWhale](https://github.com/Hmbown/CodeWhale) TUI：
深蓝底 + 橙红圆角输入框 + 底部状态行。

## 快速开始

```bash
npm install
npm start                       # 默认打开 cn.bing.com
node run.mjs https://example.com
node run.mjs "搜索关键词"        # 无点号/含空格 → 走必应搜索
node run.mjs --image https://example.com   # 切回「整页截图降采样」模式
```

Windows 下双击 `启动.bat` 亦可。

## 两种渲染模式

| 模式 | 原理 | 文字 | 适合 |
|---|---|---|---|
| **text**（默认） | DOM 提取文字 → 终端字符排版；媒体单独裁图转字符画 | 100% 清晰 | 读文章、找入口、填表单 |
| **image** | 整页截图 → 4×8 降采样 → 字符网格 | 受分辨率限制 | 看整体版式、看纯图形页面 |

交互中按 `m` 随时切换。文字模式是默认值，因为**像素网格装不下网页正文** ——
详见下面「为什么默认不用字符画渲染文字」。

## 操作

**鼠标（默认开启）**

| 操作 | 作用 |
|---|---|
| 左键点链接 | 真实点击（`target=_blank` 会在**本标签**打开，见下） |
| 左键点控件 | 聚焦该控件并进入输入模式，直接打字 |
| 左键点折叠标记 | 就地展开 / 收起**这一处**折叠内容 |
| 滚轮 | 上下滚动（文字模式按行，瞬时） |
| 按住 `Shift` 拖选 | 绕过鼠标上报，用终端自己的选择（`xterm` 系通用约定） |
| `: /mouse` | 切换鼠标上报开 / 关（关了才能拖选复制） |
| `--no-mouse` | 启动时就不接管鼠标 |

点空白处 / 纯文字段落不会做任何事，只会提示一句 —— 文字模式是**重排**过的，
终端列和页面 x 之间没有线性关系，按像素反推去乱点很容易误触广告或提交按钮。

**键盘**

| 键 | 作用 |
|---|---|
| `j` / `k` / `↓` / `↑` | 上下滚动 |
| `d` / `u` | 上下半页 |
| `g` / `G` / `Home` / `End` | 跳到页首 / 页尾 |
| `m` | 切换**文字模式 / 图片模式** |
| `v` | **元素清单**：列出页面所有可交互元素，↑↓ 选择、Enter 真实点击 |
| `Tab` | 在链接与表单间循环聚焦（整行铺金色底 + 行首 `▶`） |
| `Enter` | 打开当前聚焦的链接 |
| `i` | **进入输入模式**：自动聚焦页面的主搜索框 / 输入框，直接打字；`Enter` 提交 |
| `/` | **页内查找**：输入关键词回车定位，`n` / `N` 在命中间跳转（高亮跟随滚动） |
| `B` | 收藏当前页到书签（按地址去重） |
| `o` | 地址栏输入网址或搜索词 |

| `r` | 刷新 |

| `?` | 展开完整快捷键说明 |
| `q` / `Ctrl+C` | 退出 |

### 多标签页（交互模型参考 OpenCode V2 TUI）

顶部有一条**横向标签栏**，每个标签显示 `[编号] 标题`，当前标签高亮。
按键沿用 OpenCode V2 TUI 的那一套：

| 键 | 作用 |
|---|---|
| `Ctrl+Tab` / `Ctrl+Shift+Tab` | 下一个 / 上一个标签页 |
| `Ctrl+1` … `Ctrl+9`、`Ctrl+0` | 直跳到第 1–9 / 第 10 个标签页 |
| `Ctrl+W` | 关闭当前标签页 |
| `Ctrl+Shift+T` | 重开最近关闭的标签页 |
| `Ctrl+T` / `t` | 新建标签页 |
| `w` | 关闭当前标签页 |
| `[` / `]` | 上一个 / 下一个标签页 |
| `1` … `9`、`0` | 直跳到第 1–9 / 第 10 个标签页 |

> ⚠️ `Ctrl+数字` / `Ctrl+Tab` 依赖终端**上报修饰键**。
> Windows Terminal（kitty 协议 `CSI u` 或 win32 输入模式）可以；
> 传统 conhost 里 `Ctrl+Tab` 与 `Tab` 是同一个字节、`Ctrl+1` 与 `1` 也是同一个字节。
> 所以另配了一套**单键退路**（`t` / `w` / `[` / `]` / `1`–`0`），语义完全一致。

每个标签页是**一个真实的 Chromium 页面**（`Target.createTarget` + 独立 CDP 连接），
各自保留 URL、标题、滚动位置、折叠展开状态、页内查找高亮、渲染模式。
切换标签是**纯内存**操作（状态快照/恢复），不重新抓页。最多 12 个。

输入模式（`i`）内：

| 键 | 作用 |
|---|---|
| 直接打字 | 送进页面里当前聚焦的控件（`Esc` 前一直有效） |
| `Enter` | 提交（搜索框几乎都在 `<form>` 里，回车即提交） |
| `Backspace` | 在这个控件里退格（**不是**返回上一页） |
| `↑` / `↓` | 搜索建议下拉；焦点在 `<select>` 上时改为**换选项**（自动触发 change，真实浏览器同款） |
| `←` / `→` | 控件内文本光标（配合 `Shift` 选中文本） |
| `Home` / `End` / `Delete` / `PgUp` / `PgDn` | 控件内编辑（行首/行尾/删除/翻页） |
| `Ctrl+A` / `Ctrl+Z` | 全选 / 撤销（进页面，富文本必备；`Ctrl+C` 退出程序、`Ctrl+V` 粘贴另有通道） |
| `Tab` | 换到下一个控件 |
| `Esc` | 退出输入模式（对齐真实浏览器失焦语义：退出时对控件补发 `change` 事件，站点校验/联动立即生效） |

contenteditable 富文本（在线编辑器、评论框、聊天输入框）也是一等公民：
会被提取为控件（`v` 清单和文字流里可见），打字/退格/全选与普通输入框一致。

### 元素清单模式（`v`）—— 解决「找不到入口 / 点不动」

现代站点大量用 `div` + 事件委托实现按钮（知乎的「验证码登录」就是 `div`），
`Tab` 键**永远聚焦不到**它们，所以按 Tab + Enter 也没用。

`v` 模式绕开像素，直接读 DOM：

1. 枚举页面上所有可见、可交互元素（`a[href]` / `button` / `input` /
   `[role=button]` / `[onclick]` / `[tabindex]` / `[onmouseover]` …）
2. 视口内的元素在画面上打上**金色编号**，选中项用**橙红描边框**标出
3. `↑↓`（或 `j/k`）切换，选中项若在折叠线以下会**自动滚动带进视野**
4. `Enter` 用 `Input.dispatchMouseEvent` 派发**真实鼠标点击**，
   而不是 `el.click()` —— 后者对 React 合成事件无效；文件控件（`input[type=file]`）
   的 Enter 直接进入上传流程（见下）
5. `h` **悬停**选中元素（只移鼠标不点击）—— 导航下拉菜单、hover 提示
   由此展开；鼠标随后停在子项上时父菜单的 hover 链保持（真实浏览器同款），
   再 `↑↓` + `Enter` 点击子项即可
6. `d` **双击**（真实连击语义）：`dblclick` 事件、选中文本由 Chromium 合成 ——
   双击选词后可用 `Ctrl+C` 通道复制
7. `g` **拖拽**：第一次按标记起点，`↑↓` 移到目标元素再按一次落下。
   派发「按下 → 分步移动 → 松开」的**真实鼠标序列** —— 滑块验证码、
   拖拽排序列表就是靠它；两端元素都必须在视口内
8. `u` **上传文件**（仅 `input[type=file]`）：输入本地路径（多个用 `|` 分隔）→
   CDP file chooser 拦截写入 `input.files` 并补发 `change` —— 站点的
   「已选文件」回显与提交校验都正常触发

**iframe 内嵌页面**：登录组件、验证码、支付面板大量内嵌 iframe。同源 iframe
的内容文字直接并进主文档流（看得见），内部按钮/输入框进元素清单（点得到、
打得进，坐标跨 frame 自动换算）；跨源 iframe 受浏览器安全模型限制，
如实标注「内容不可读」占位，不假装读到。

### 折叠内容（`e` / `E`）—— 解决「正文被折叠了看不全，又点不动」

投诉原话：「页面缺乏交互，很多文字部分被页面折叠了看不全，无法点击展开和查看详细」。

根因是**双重的**：折叠正文大多是 `display:none`（或 closed `<details>`），
旧提取器对隐藏元素一律过滤 —— 正文**整段消失**；而那个「展开全文」按钮是站点的
`div` + 合成事件，文字浏览器又点不动。于是用户只看到四个字，没有任何办法。

现在的分工：

| 键 | 做什么 | 副作用 | 展开后链接可点？ |
|---|---|---|---|
| `e` | 把折叠正文**读出来就地插进文本流**（暗色显示） | 无 | 否（纯文本） |
| `E` | **真去点**页面的展开控件 + 解除 `line-clamp`/`max-height` 截断，再重新提取 | 会动页面 | **是** |

`e` 是主力：折叠内容的**文字本来就在 DOM 里**（`display:none` 只是不渲染），
直接读出来最稳 —— 不依赖站点 JS、不触发埋点、不会跳走，而且是瞬时的
（不重新抓页面、不重新截图）。`E` 用来兜那些「点了才发请求注入」的内容
（「加载更多评论」之类）。

收起状态下，页面上会留一行**显眼的金色标记**，把「这是什么、多少字、按哪个键」
讲清楚，而不是让内容无声消失：

```
▸ ▣ 折叠内容 · 展开全文 · 1284 字 · 按 e 展开 │ 这是被折叠起来的详细内容第一段…
```

按 `e` 之后：

```
▾ ▣ 展开全文 · 已展开 1284 字 · 按 e 收起
  这是被折叠起来的详细内容第一段……
```

底部提示行常驻显示 `折叠 0/3 处 (e 展开·收起)`。

**默认收起而不是自动全展开**，理由和「媒体分级」是同一条：站点为窄视口藏起来的
**导航菜单**也会被识别成折叠内容（实测 Bing 的隐藏导航 99 字、MDN 的侧边导航
1790 字）。全展开会把正文顶到几十屏之外 —— 正是「找不到登录入口」那类事故的翻版。
现在它们只占 1 行标记，展开与否由用户决定。

### 表单控件（`i`）—— 解决「看不到搜索框，无法搜索」

投诉原话：「Bing 页面看不到搜索的输入框，无法搜索」。

根因很朴素：**`<input>` 自身没有文字节点，也不是媒体块**。旧提取器走到
「只收叶子文字块」那一步时 `directText` 为空，直接 `continue` ——
于是必应首页那个 **659×42、明明白白可见**的搜索框在文字模式里**完全不存在**，
页面看上去根本没有搜索功能。（诊断脚本：`tests/probe-fields.mjs`）

现在表单控件是一等公民，固定占一行：

```
▢ 搜索框「站内搜索」 ▸ 已输入的内容  [ 搜索 ]  按 i 输入
▢ 文本域「留言」 · 空                          按 i 输入
▢ 下拉框「城市」 ▸ 上海                        按 i 输入
▢ 输入框「禁用框」 · 已禁用
```

配色即语义：**青色**=可以打进去，**金色**=提交按钮，**灰色**=禁用/只读。
正在输入的那个控件前面是 `▶` 而不是 `▢`。

按 `i` **直接聚焦页面的主搜索框**，不需要先 Tab 蒙一遍（旧流程要求
「先按 Tab 聚焦输入框再按 i」，而必应首页的搜索框既看不见、又不在 Tab 顺序前面，
用户就卡死在这句话里出不来）。

**「主搜索框」怎么判**（`extract.js` 里算分，实测必应首页 180 分）：

| 判据 | 加分 |
|---|---|
| `type="search"` | +100 |
| `name` 是 `q` / `query` / `wd` / `kw` … | +40 |
| 在 `[role=search]` 或 `action` 含 search 的表单里 | +30 |
| 名称/占位符含「搜索 / search」 | +25 |
| 宽 ≥ 120px | +10 |
| `disabled` / `readOnly` / `checkbox` | 大幅减分 |

名称显示也做了过滤：`name="q"`、`id="sb_form_q"` 这种机器标识**不给用户看**
（必应首页会变成「搜索框「q」」，比不显示还糟），只显示 `<label>`、`aria-label`、
`placeholder`，都没有就只写「搜索框」。

**两个实现要点，都踩过**：

1. **定位走 `data-etui-field` 编号，不走坐标点击。**
   窄视口下表单常比整个视口还宽，元素中心点落在视口外就点空了
   （知乎手机号输入框就是）。提取时把编号写进 DOM，`focusField(fid)` 直接查。
2. **CDP 派发 `Enter` 必须带 `text: "\r"`。**
   只发 `keyDown` 的话浏览器只产生 `keydown`，**没有 `keypress`**，
   而 `<form>` 的隐式提交挂在 keypress 之后的默认行为上 ——
   症状是「在搜索框里按回车毫无反应」，从 DOM 侧完全看不出原因。
   实测对照见 `tests/probe-enter.mjs`：

   | 派发方式 | 事件 | 表单提交 |
   |---|---|---|
   | `keyDown` + `keyUp` | `keydown` | ✗ |
   | `rawKeyDown` + `keyUp` | `keydown` | ✗ |
   | 带 `text:"\r"` | `keydown` `keypress` | ✓ |

另外，**打字不会触发整页重抓**：每敲一个字符只做一次 `evalJs` 读回控件
`value`，然后重绘内存里已有的排版结果。完整 `capture()` 会重新提取 DOM
**并给页面上每个图片/二维码重新截图**（知乎那种页面 4 个媒体块、二维码还要
2× 超采样），逐字符跑一遍又慢又闪。

#### 输入走的是「自愈」链路 —— 解决「打不进 / 退不掉 / 搜不出」

投诉原话：「搜索结果无法显示，输入法在搜索框无法正常显示，输入关键字不可退格」。

三个症状看着是三件事，实测下来是**同一个根因**，而且能精确复现：
`Input.insertText` 把字送进浏览器**内部记住的那个焦点元素**，不是
`document.activeElement`。站点把输入框节点换掉之后（SPA 重挂载、框架重渲染、
focus 后换新节点 —— 真实站点上很常见），内部焦点仍指着**已经被摘掉的旧节点**，
于是：

| 动作 | 结果 | 用户的说法 |
|---|---|---|
| 打字 | 字打进虚空，控件 value 一个字节不变，**不报错** | 「输入法/输入框不显示」 |
| 退格 | 值本来就没进去，没什么可删 | 「输入关键字不可退格」 |
| 回车 | 提交的是空值 | 「搜索结果无法显示」 |

实测对照（`tests/probe-node-swap.mjs`）：

```
A 正常聚焦后 insertText("A")    → value="A"   ✓
B 节点被替换后 insertText("B")  → value=""    ✗ 完全静默失效
C 重新聚焦再送 insertText("C")  → value="C"   ✓ 一级自愈即可恢复
E 焦点在 textarea 时送字        → 字进了 textarea，搜索框纹丝不动
```

所以 `src/inputpath.js` 把每个动作都做成**三步 + 读回校验**，并且**先查焦点**：

| 级 | 手段 | 什么时候用上 |
|---|---|---|
| `direct` | 真实按键 / `insertText` | 焦点本来就在目标控件上（绝大多数时候） |
| `refocus` | 先 `focusField` 再送 | 节点被换掉、焦点跑偏（实测场景 B/E） |
| `dom` | 原型 setter + 派发 `input` 事件 | 连 `focus()` 都失效（站点自绘控件） |

**为什么必须"先查焦点"**：焦点在别的控件上时直接送字，字会落进**那个**控件
（实测场景 E）。修焦点要在送字之前，不能等失败再补救。

**为什么要读回校验**：上面那三种失效**全部是静默的** —— 不抛错、返回值正常。
没有校验就无从知道"这一键到底进没进去"，也就谈不上兜底。
自愈发生时状态栏会写出来（`（已自动重新聚焦）` / `（已改用 DOM 输入）`），
`crash.log` 里也有 `[input] … 走了兜底路径` —— **自愈必须是看得见的**。

**提交带看门狗**：发一次**真实回车**（会走浏览器的隐式提交与站点的按键处理器），
用**地址有没有变**做成功判据。地址没变 ≠ 失败 —— AJAX 表单（登录、发验证码、
即时搜索）本来就不跳转，此时如实报告并抓一帧让用户看到站点的弹层/提示反馈。
「拿关键词直达搜索地址」的兜底只对**确认是搜索场景**的控件生效
（`type=search` / 文案带搜索字样 / 搜索引擎站点）—— 否则会把用户刚输的
手机号当搜索词跳去 Bing，表现就是「获取验证码把整个页面刷新了」
（复现与验证见 `tests/probe-sms.mjs`）。

**输入永远看得见**：`i` 模式下底部输入框会镜像显示页面控件的当前值
（`» 安徽招标`），并且会把控件所在行**滚进可视窗口**。
在此之前，用户打完字在最顺手的位置（底部输入框）什么也看不到，
控件行又可能在屏幕外 —— 会被直接判定成"输入法坏了"。

**输入中文**：`Ctrl+V` 粘贴是最可靠的路子（终端把整段 UTF-8 直接交给我们，
绕开 IME 组合过程；我们主动开了括号粘贴上报 `?2004h`，一次粘贴是一个整体事件）。
Windows 传统控制台（conhost）里的 IME 常常打不出字 —— 那是 conhost 与原始模式
不对付，启动时会提示换 Windows Terminal。排查终端到底送来了什么字节，
用 `set EDGE_TUI_KEYS=1`（每个按键事件都写进 `crash.log`）。

### 鼠标 —— 参考 Browsh 补上的主路径

键盘路径（`Tab` 循环 / `v` 元素清单）是「没有鼠标时」的兜底，不能当主路径：
它们要求用户先知道有这两个功能，再盯着屏幕找行号。而人看到链接的第一反应就是点。

Browsh 靠 `tcell` 直接拿鼠标事件。我们没有 native 依赖，自己解 **SGR 扩展编码**
（`ESC [ < Cb ; Cx ; Cy M`）—— 协议本身很简单，真正麻烦的是另外三件事：

**① 必须用 SGR（`1006`）而不是老式 X10 编码。** X10 把坐标压在单个字节里，
列号一过 223 就溢出。这个浏览器的页面区经常在 200 列以上，用 X10 会点错位置。

**② 序列可能被 chunk 切开。** 终端一次 `read` 可能正好把 `\x1b[<0;10;5M`
从中间切断。解析器对「不完整」必须返回 `null` 等下一批，不能把半截当无效字节吞掉
——否则后半截会被当成普通字符打进输入框。

**③ 「点在哪个块上」不能靠坐标反推。** 文字模式是**重排**过的，终端列和页面 x
之间没有线性关系。所以渲染时给每个 run 挂上 `src`（它来自哪个 DOM 块），
点击时按 run 的宽度累加做命中 —— 这样才可能点得准。

配套的一个非平凡改动：**行内合并的行必须逐段记录来源块**。
`登录 注册 帮助中心` 这种导航行会被排版层拼成一行，如果整行只记一个来源块，
点「注册」就会打开「登录」。现在每个片段各带自己的块和样式
（顺带修掉「一个链接把整行染蓝」），点哪段是哪段。

**顺带修掉两个只有真实站点才暴露的 bug：**

| bug | 症状 | 根因 |
|---|---|---|
| 枚举编号错位 | 本地页面一切正常，真实站点「点了没反应 / 点 A 开了 B」 | `enumerateInteractive` 分两次查询：结果数组按**矩形去重**，而 `clickIndex` 索引的 `window.__etuiEls` 不去重。页面上只要有一组等尺寸元素（必应导航图标、列表按钮），两个数组下标就错开 |
| `target=_blank` 静默吞掉点击 | 点了完全没反应，地址不变、画面不变 | 文字浏览器只有一个 tab，Chromium 在后台开了个新标签。现在点击前把锚点与 `<base>` 的 `target` 掰成同标签（实测必应首页带 `href` 的链接大半是 `_blank`） |

两个 bug 都加了夹具（等尺寸叠放按钮 / `_blank` 链接）并做过**故障注入验证** ——
把修复回退掉，套件立刻变红。

命令模式（`:` 或 `o` 下以 `/` 开头）：

```
/reload  /back  /forward  /top  /end  /bm  /his  /mouse  /quit
```

`/bm` 书签列表 · `/his` 历史列表（`↑↓` 选择、`Enter` 打开、`x` 删除、`Esc` 退出）。

## 像常见浏览器：登录态、页内查找、书签、历史

| 能力 | 用法 | 说明 |
|---|---|---|
| **登录态保留** | 默认开启 | 持久 profile（`%LOCALAPPDATA%\edge-tui\profile`）：Cookie/LocalStorage 跨会话保留，登录一次以后还在。退出时先 `Browser.close` 优雅关闭再杀进程树 —— Cookie 是内存态，强杀会丢（localStorage 走写前日志不受影响，症状极具迷惑性） |
| **页内查找** | `/` 进入，`Enter` 定位，`n` / `N` 跳转，`Esc` 取消高亮 | 纯内存：在已提取的排版行上匹配（大小写不敏感），命中行铺底色、当前命中更亮。不碰浏览器、不重新抓页 |
| **书签** | `B` 收藏当前页，`/bm` 查看 | 按地址去重；存 `%LOCALAPPDATA%\edge-tui\bookmarks.json` |
| **历史** | 自动记录，`/his` 查看 | 新→旧，连续同一地址去重，上限 1000 条；存 `%LOCALAPPDATA%\edge-tui\history.json` |

| 参数 | 说明 |
|---|---|
| `--fresh` | 本次用一次性临时 profile（退出即删，旧行为） |
| `--reset-profile` | 清空持久 profile 后启动（登录全部重来；书签/历史不受影响） |
| `--clean` | 清理残留的 Edge **临时** profile 目录并退出（不动持久 profile） |
| `--user-agent=UA` | 伪装 UA。headless 下部分站点会主动降级（必应返回精简版首页：无导航、无背景图），伪装成正常浏览器能换回完整版 |

## 一次渲染整页：滚动不再重新加载

用户问：「每动一下就要重新加载，是不能一次渲染整个页面吗？」

**能，而且本来就是这么设计的** —— 文字模式下 `buildTextPage` 用 `viewport: false`
**一次性提取整个文档**（不是只取可视区），所有媒体图也在同一次里抓完
（`screenshotClip` 带 `captureBeyondViewport: true`，视口外的图照样抓）。
所以排版结果完整躺在内存里，滚动只需**挪行窗口 + 重排**。

但 `scrollPx` 的文字模式分支里写着 `await capture()` —— 每滚一步都重新走了
「等内容稳定 → 重新提取 DOM → 给每个媒体块重新截图」的完整流程。
注释写的是"不必让页面重新滚动/截图，让滚动变得瞬时"，代码却在做相反的事。

实测每一步滚动的成本：

| 页面 | 旧（每滚一步 = 一次完整抓取） | 新（纯内存重排） |
|---|---|---|
| 必应首页（37 行 / 3 张图） | **903ms** | 0ms |
| 合成重页面（241 行 / 40 张图） | **2727ms** | 7ms |

同一处浪费还出现在 `Tab` 切焦点（`focusNext`）和点输入框（`focusFieldBlock`）上 ——
它们都只改变了"焦点/显示位置"，页面内容一个字节都没变，却各跑了一次整页抓取。

**现在哪些动作碰浏览器、哪些不碰**：

| 动作 | 碰浏览器？ | 说明 |
|---|---|---|
| `j` `k` `↑` `↓` `d` `u` `g` `G` 滚轮 | **不碰** | 整页已在内存，只挪行窗口 |
| `Tab` 切换焦点 | **不碰** | 焦点高亮只改内存里的行 |
| `e` / 点折叠标记 展开收起 | **不碰** | 折叠正文本来就在 DOM 里，展开是文本层的事 |
| 点输入框 / `i` 进输入模式 | 只读一次控件值 | 焦点变了，页面内容没变 |
| 输入模式下打字 / 退格 | 每次按键读一次控件值 | 不重抓整页（见「表单控件」一节） |
| 点链接 / `Enter` / `r` / 前进后退 | 必须碰 | 页面真的换了 |
| 输入模式下 `↑` `↓` 选搜索建议 | 必须碰 | 建议下拉是页面自己变的 |
| `m` 切图片模式 | 必须碰 | 像素网格只能按视口截 |
| `v` 元素清单 | 一次 DOM 查询 | 枚举可交互元素，不截图 |
| `/` 查找 · `n`/`N` 跳转 | **不碰** | 整页排版在内存里，匹配 + 高亮 + 挪窗口都是纯内存 |

文字模式下抓完页状态栏会写明：`就绪 · 全文 412 行已装入内存（滚动不再重新加载）`。

**回归防线** `tests/test-noreload.mjs`：把 run.mjs 以 `EDGE_TUI_NO_MAIN=1` 导入测试进程
（`run.mjs` 导出了 `__test` 挂载点），塞进一个**会计数的 tab 替身**，
断言「文字模式连滚 30 次对浏览器 **0 次调用**」，并检查边界钳制
（滚到顶/到底不越界）与源码层面「文字分支里不许出现 `capture(`」。
`tests/probe-scrollcost.mjs` 给出上面那张耗时表。

## 不会卡住：加载等待策略

用户反馈「总是会有莫名其妙的页面加载卡住」。查下来不是一处问题，而是**每一步都可能无限等**，
而且每一步单独看都"很合理"：

| 病灶 | 旧行为 | 后果 |
|---|---|---|
| 等 `Page.loadEventFired` | 最多 **25 秒** | 广告/埋点/大图任一卡住，`load` 永远不来 |
| 之后的 `settle()` | 最多 **12 秒**，且要求 `readyState === 'complete'` | 有挂起子资源时 complete 永远不来 → 每轮白等 |
| 串行抓图 | 无上限 | 40 张图 = 40 次 CDP 往返，界面完全静止 |
| `alert()` / `confirm()` | **完全没处理** | 弹窗阻塞渲染进程，`evaluate`/截图全部不返回 → 永久冻死 |
| WebSocket 断开 | 每个在飞调用各自等 30 秒超时 | Edge 崩了一次，界面冻两分钟 |

**同类项目的做法**（抄结论，不抄代码）：

| 项目 | 模型 | 等待策略 |
|---|---|---|
| w3m / lynx / elinks | 纯 HTTP 解析 | **不等** —— 收到 body 就渲染，从不等子资源 |
| Browsh | Firefox + 取帧 | DOM 就绪 + `render_delay = 100ms`；`timeout = 30s` 是硬上限；**不等 load 事件** |
| Carbonyl | 真 Chromium + 连续出帧 | **根本不"等加载"** —— 什么时候画出来什么时候算；需要时 `--wait-for <selector>` |
| Playwright / Puppeteer | 自动化 | 默认 `waitUntil:'load'` 是**最慢最脆**的选项，官方文档明说重广告站点要改 `domcontentloaded`；强调**永远不要 `timeout=0`**（会把"慢加载"变成"静默死循环"）；`networkidle` 在有埋点/长连接的页面上可能永不返回 |

结论是一致的：**别把「所有资源加载完」当可用条件**，改成「**新文档就位 且 内容连续两拍不变**」，
并且每一步都留硬上限。现在的实现：

```
Page.navigate ──► 打上「旧文档」标记（确认之后看到的是新页面）
   │
   ├─ 错误立刻回报          errorText 非空（域名解析不了/连接被拒）→ 立即返回
   ├─ 内容已丰富           文本 > 1500 字 → 立即返回
   ├─ 新文档 + 内容稳定两拍  ≈ Browsh 的 render_delay 之意
   ├─ 空页面快速收手        body 都不存在（head 里脚本挂住）→ 4s 后报 stalled
   └─ 硬超时 12s            **返回 degraded 而不是抛错** → 渲染已加载部分 + 说明
```

**为什么判据里绝不能出现 `readyState`**：`<head>` 里一个不返回的 `<script src>`
会让 HTML 解析器直接停住，`DOMContentLoaded` 和 `readyState !== 'loading'`
**都永远不会发生**。本地脚本总是立刻返回，所以静态页面手工测试永远复现不出来 ——
但线上被墙/被拦的统计脚本天天这样。

配套的三件事：

- **弹窗自动关掉**（`Page.javascriptDialogOpening` → `handleJavaScriptDialog`）并记账，
  状态栏会写「已自动关闭 N 个页面弹窗」。这是**唯一**能解开"永久冻死"的办法。
- **抓图预算**：先抓信息量大的（二维码 → 大图 → 中图），超预算/超时/被中断的退化成
  一行写明原因的占位（`▫ IMG 图片4 300×200 · 未抓取（超出本次抓图预算（4 张））`）。
  抓图期间状态栏会动（`正在抓取图片 6/24…`）—— 有动静就不像卡死。
- **`Esc` = 停止加载**（浏览器的"停止"按钮）：打中断标记 + 停进度条 + 真发
  `Page.stopLoading`。在此之前一旦卡住，除了退出程序没有任何办法。

超时可调：`EDGE_TUI_NAV_TIMEOUT`（默认 12000）、`EDGE_TUI_MAX_SHOTS`（默认 24）、
`EDGE_TUI_CAPTURE_BUDGET`（默认 20000）。

**回归防线**：`tests/test-loadhangs.mjs` 起一个**永不回应**的本地 HTTP 服务器，
确定性地制造出上面四种状态，用**墙上时钟**断言。实测：

```
① 图片永不返回         501→767ms（旧实现 25s + 12s），且确认 load 从未触发
② 阻塞脚本在正文中     388ms，且能读到脚本之前的正文
②' 阻塞脚本在 head      4213ms → 报「没有内容」而不是等满超时
③ onload alert()       362ms，弹窗自动关闭，之后仍能 evaluate + 截图
④ 30 张大图            1838ms → 255ms（预算 4 张，其余写明原因）
⑤ 域名解析失败         407ms，带回 net::ERR_NAME_NOT_RESOLVED
⑥ 浏览器断开           3ms 报「CDP 连接已断开」（不是 30s）
```

### 为什么默认不用字符画渲染文字

这是本工具最重要的一次架构修正。旧方案把整页截图按 4×8 像素降采样成字符网格，
于是**文字和二维码一起变成噪声**：

- 单元格 4×8 像素，而网页表单文字通常 14px，一个汉字横跨约 3.5 个格子，
  笔画细节必然丢失 —— 正文糊成一团，登录入口根本认不出来
- 二维码是高频图案，降采样后变成一片 `@`，看不清也扫不了

新方案的分工很明确：**文字走 DOM，图走像素**。文字从 DOM 取，准确率 100%，
不受任何分辨率限制；只有真正需要"看形状"的图片区域才转字符画。

### 阅读顺序用 DOM 文档顺序，不用几何坐标排序

初版按 `(y, x)` 几何坐标给块排序，遇到多栏布局就崩：知乎登录页左侧扫码面板
和右侧登录表单的 y 区间交错，几何切分永远找不到一条干净的"栏间空隙"。

DOM 顺序本身就是作者编排的阅读顺序 —— 左栏读完读右栏，最后读页脚，
**和几何排序的结果通常一致，但多栏、浮动、绝对定位下更稳**。
这也正是 w3m / lynx 的做法。

### 媒体按「信息密度」分级，不按原始尺寸

早期公式对每个媒体一律给相同的行数上限，结果 20×20 的 favicon 和 138×138 的
二维码同样占 14 行。知乎登录页 4 个媒体块吃掉 66/98 行，
「验证码登录」被挤到第 42 行，而首屏只有 28 行 —— **用户找不到登录入口**。

现在分四档，尺寸由「这块图里有多少可读信息」决定：

| 档位 | 判定 | 给多少行 | 理由 |
|---|---|---|---|
| `qrcode` | alt 含二维码/扫码/条码，或 `<canvas>` 近正方形且 ≥88px | 9 | 承载数据，必须看清定位角 |
| `photo` | 最长边 ≥ 200px | 6 | 只需轮廓示意 |
| `small` | 其余有图块 | 3 | 一笔带过 |
| `icon` | 任一边 < 40px | 0（一行占位） | 纯装饰，没有可读信息 |

降采样比例约 6:1。若行数被上限截断，**不再反过来按行数压缩列数** ——
否则 128×81 的 LOGO 会退化成 9×3 的一小撮噪点；宁可接受轻微纵向压缩，
也保住能辨认的横向轮廓。

效果：知乎登录页总行数 98 → 50，「验证码登录」从第 42 行提到第 **24** 行，直接进首屏。

### 折叠内容：探测要「有控件才算数」，展开要「走文字层」

正文被站点折叠起来有两类载体，处理方式不同：

| 载体 | 隐藏方式 | 文字还在 DOM 里？ | 处理 |
|---|---|---|---|
| `display:none` 的手风琴 / 折叠面板 | 计算样式 | ✅ 在 | 登记成折叠块，`e` 就地展开 |
| closed `<details>` | UA 样式（摘要之外不可见） | ✅ 在 | 同上，标记排在 `<summary>` 之后 |
| `-webkit-line-clamp` / `max-height` 截断 | 视觉裁剪 | ✅ 在 | **本来就该读到**，无需展开 |
| 「加载更多 / 下一页」 | 点了才发请求 | ❌ 不在 | 只能 `E` 真实点击后再提取 |

两个关键设计：

**① 探测判据必须包含「附近有展开控件」，不能只看到 `display:none` 就算。**
站点里有大量隐藏的弹窗模板、埋点 div、菜单骨架，只按「隐藏 + 有文字」判定，
正文立刻被这些垃圾淹掉。所以要求：隐藏子树 ≥12 字 **且**
能找到展开控件（`aria-controls` 指名 → 紧随其后的兄弟 → 祖先容器内
带 `aria-expanded` 或「展开/更多/详情/全文」字样的可见控件，逐级放宽）。
找不到控件就当普通隐藏内容丢弃，并把字数累计到 `droppedHidden` 供诊断。

**② 展开在文字层做，不去点页面。** `applyFoldState()` 把折叠行的正文
按终端宽度重新折行后插进 `lines`，因此：
- 不依赖站点 JS（`div` + React 合成事件那套点不动，坑见「元素清单」一节）
- 不产生副作用（不触发埋点、不跳转、不改页面状态）
- 瞬时完成（排版结果已在内存里，不重新抓页面、不重新截图）

带来两个必须守住的约束：
- **幂等**：每次都从 `page.linesBase` 重建，绝不在 `page.lines` 上追加 ——
  否则反复按 `e` 会把正文重复插进去。
- **`renderedRowCount` 仍然成立**：展开插入的都是普通 `text`/`blank` 行（各占 1 行），
  所以叠加层的行映射不用改。测试里对展开态专门断言
  「`renderedRowCount` 累加 === `renderTotalRows`」。

隐藏子树取文本用**递归遍历 + 剥掉 `script/style`**，而不是 `innerText` ——
元素不可渲染时 `innerText` 会回退到 `textContent`，把 `<script>` 源码一起带出来。

### 二维码：不降采样，1 模块 = 1 字符

这是 `qrcode` 档和别的媒体档**根本不同**的地方：别的图只要"看出形状"，
二维码却承载着数据，**降采样就是毁数据**。

旧路线把二维码截图后压成 9 行字符画。知乎的码是 **49×49 模块**，
压进 9 行等于每行塞 5.4 个模块 —— 信息丢了 40 倍，除了"这里有个二维码"
什么也读不出来。作为对照，`tests/test-qr-scan.mjs` 会把这种图喂给真正的
解码器（jsQR），确认它**必然解不出**。

正确做法来自 `qrencode`：**从不经过降采样**，模块矩阵直接映射成字符。
网页里的二维码本来就有确定的模块矩阵，把它还原出来即可。

**① 为什么走截图，而不是 `canvas.getImageData()`**

知乎登录页的二维码是 `<canvas class="Qrcode-qrcode">`，但它内部是用**跨域图片**
绘制的 —— canvas 已被污染，`getImageData()` 直接抛 `SecurityError`，一个像素都读不到。
截图取的是浏览器自己的合成结果，不受同源策略限制，对 `canvas` / `img` /
CSS 背景图一视同仁。分辨率也够：138px 的码里 49 个模块约 2.8px/模块，
**超采样 2×** 后约 5.6px/模块，边界清晰（实测采样纯度 0.99）。

**② 截图的 clip 是「视口坐标」，不是「文档坐标」**

这点极容易搞错。块的坐标按 `extract.js` 的约定是**布局坐标**（与滚动无关），
但 `Page.captureScreenshot` 的 `clip` 用**视口坐标**。实测：

| 页面滚动 | 用布局坐标截 | 用视口坐标截 |
|---|---|---|
| 0px | ✓ n=49 | ✓ n=49 |
| 200px | ✗ 截到空白 | ✓ n=49 |

页面没滚时两者重合，**一滚就错**。所以每次截图前必须减掉总滚动量
（`PAGE_META` 里的 `scrollLayoutX/Y`）。这条同样修掉了 ASCII 图片旁路里
一个潜伏的 bug —— 那些媒体图在页面滚动后也会截错位置。

**③ 模块数是猜出来的**

QR 的版本决定边长（version 1..40 → 21, 25, …, 177），但页面上没有任何标记
告诉我们用的是哪一版。做法是**全猜一遍再选最像的**：对每个候选 n 把符号切成
n×n 格、采样每格中心 42% 见方，统计"成色纯度"。

- 正确的 n → 每格要么全黑要么全白，纯度接近 1
- 错误的 n → 大量格子跨在模块边界上，纯度接近 0

最后用三个 7×7 定位角做硬校验，杜绝把方形 logo 误判成二维码。

**④ 两种渲染比例**

| 比例 | 1 模块 = | 一行装几个模块行 | 用什么画 |
|---|---|---|---|
| `full` | 2 字符宽 × 1 字符高 | 1 | 空格 + **背景色** |
| `half` | 1 字符宽 × 半字符高 | 2 | `▀▄█` 半块字符 |

`full` 的模块面积是 `half` 的 **4 倍**，屏幕成像清晰得多，所以**能放下就用 full**。
但终端只有约 28 行，49 模块的码用 full 需要 57 行 —— 装不下，只能退到 `half`
（27 行）。

`full` 刻意**不用 `█` 字符**，而是用"两个空格 + 背景色"铺色块：`▀▄█`
（U+2580–259F）在 Unicode 里的 East Asian Width 是 **Ambiguous**，
遇到"歧义宽度按双宽处理"的终端会被画成 2 列，二维码横向拉长一倍就彻底扫不出来。
空格永远是 1 列，零风险 —— `qrencode -t ANSI256` 用的也是同一招。

**⑤ 强制黑白，并且必须整块可见**

无论哪种比例都强制前景黑、背景白。深色终端主题下若沿用默认前景色，
画出来是"白点黑底"的**反色码**，不少扫码器不认 —— 这正是上游
[wireguard-install #41](https://github.com/Nyr/wireguard-install/issues/41)
那类"二维码扫不出"报告的同源问题（上游后来的修法就是从 `-t UTF8`
换成 `-t ANSI256UTF8`，强制黑白配色）。

静区（白边）规范要求 4 模块，终端尺寸不够时逐级退让到 3 / 2，
但**不接受 1 或 0** —— 静区只剩一格时页面底色会直接贴到定位角上。
真放不下就退到 `half` 比例，而不是牺牲静区。

另外，二维码**必须整块落在一屏内**：手机一次只能拍到一屏，缺一半的码解不出来。
它在文本流里的位置由页面决定，很容易正好卡在页面区下沿（实测知乎的码
露了 18/27 行，缺掉左下定位角），所以打开页面时若二维码未被完整显示，
会自动把行窗口对齐过去。

**⑥ 怎么证明它真能扫**

`tests/test-qr-scan.mjs` 不是"看着像就通过"，而是**把渲染结果反解回文本**：

```
文本 → 模块矩阵 → qrToCells() 字符网格
     → 模拟终端把字符画成像素（空格=背景色，▀▄█=前景色铺半格/整格）
     → jsQR 解码 → 比对原文
```

走完这一圈还能拿到原文，才说明字符网格是**信息无损**的。实测知乎登录页的码
解出 `https://www.zhihu.com/account/scan/login/MzI3N...` —— 这是从**字符**
解出来的，不是从原图。

### 坐标必须是「布局坐标」，且叠加要按二维重叠匹配

文字模式只在进入页面时提取一次 DOM，之后用户按 `Tab`、走元素清单都可能让页面
真的滚起来。如果块坐标用的是视口相对坐标（`getBoundingClientRect()`），
**页面一滚，之前提取的坐标就全废了** —— 元素清单的行首标记和整行高亮会整体偏移。

所以 `extract.js` / `enumerateInteractive` / `scrollElIntoView` / `ensureVisible`
统一输出**布局坐标**：在视口坐标基础上加回自身之外所有滚动祖先的
`scrollTop`/`scrollLeft`，以及 `window.scrollX/Y`。这样坐标与滚动无关。

只加 `window.scrollY` 是不够的：很多站点（知乎登录页就是）`body` 不滚，
内容放在固定高度的 `overflow:auto` 容器里，必须把容器的 `scrollTop` 也加回来。

拿到坐标之后，还要解决「文档坐标 → 渲染行」的映射。这里踩过两个坑：

1. **不能用 y 单调插值**。阅读顺序是 DOM 文档顺序，多栏页面的 y 会来回折返 ——
   知乎登录页先排完左栏扫码面板（y 38…584），再排右栏登录表单（y 159…563）。
   单调插值会把这次折返当成"同一段"，于是 y=159 被夹在 y=38 和 y=241 之间
   算成第 3 行，而实际是第 23 行。

2. **也不能只用「y 最近」**。多栏布局里两栏的纵区间是**交叠**的：
   「打开知乎App」（左栏 y 241…262）和「中国 +86」（右栏 y 245…264）
   都会认领 y≈245，只按 y 找必然认错栏。

正确做法是**二维矩形重叠匹配**：取与目标矩形重叠面积最大的锚点，
完全无重叠时（元素是包裹层、本身不是文字块）退化为最近距离。
所以 `makeLineMapper` 的签名是 `(y, x, w, h)` —— **只传 y 会失去横向分辨力**
（实测命中率 2/4 → 4/4）。

另外，`v` 元素清单在文字模式下的高亮**不是方框**：文字排版里没有
「像素 → 列」的线性映射（一个终端格是一个汉字，位置由折行决定），
硬套 `colsPerPx` 只会在宽字符处越界、在折行处错位。
改成文字浏览器惯用的表达：**整行铺底色 + 行首标记**（`·` 可交互 / `▸` 选中 / `▶` 焦点）。

### 滚动必须问页面「谁在滚」

很多站点不用 `body` 滚动，而是把内容放进固定高度的 `overflow:auto` 容器
（知乎登录页是 `.SignFlowHomepage`：`scrollHeight 1002 / clientHeight 224`）。
此时 `window.scrollBy` 完全无效、`window.scrollY` 永远是 0，
页面看起来「不能滚」、底部内容永远够不着。

现在 `scrollTarget()` 先判断 `window` 能否滚，不能则找**内容溢出最严重**的
可滚动元素并缓存到 `window.__etuiScrollEl`，之后 `scrollBy` / `scrollState`
全部作用于该容器。元素定位同理：逐级向上找最近的滚动祖先做居中。

文字模式下视口不参与滚动 —— 排版结果一次性生成，`j/k` 直接改**行偏移**，
因此长页面（181 行）滚动是精确到行的，不受内层容器干扰。

### 点击坐标要用「元素与视口的交集中心」

窄视口下表单常比视口宽：知乎手机号输入框 `x=317 w=241` → 中心 `x=438`，
而视口只有 432px 宽，`elementFromPoint` 返回 `null`，点击落空。
`clickIndex()` 改为求元素矩形与视口的**交集**再取中心并夹到视口内，
元素完全在视口外时返回 `offscreen` 标记而不是发一个无效点击。

### 叠加层必须映射到「渲染行」而不是「排版行」

`v` 元素清单的标记要画在正确的行上，靠 `makeLineMapper` 把布局坐标映射成行号。
这里有个坑：媒体块会展开成多行（标签 + 字符画），
所以**排版行号 ≠ 渲染行号**。映射时先用 `renderedRowCount()` 累加出每条排版行
的起始渲染行号，再在锚点间匹配，否则图片以下的标记会整体上移错位。
`tests/test-overlay-align.mjs` 会断言 `renderedRowCount` 的累加值严格等于
`renderTextPage` 的 `totalRows`，并把「只传 y」的命中率作为反例一并钉住。

### 图片模式：字符映射的四个关键点

**1. 墨量方向必须与字符密度一致。**
`RAMP = " .,:;irsXA253hMHGS#9B&@"` —— 索引 0 最空、末尾最密。
早期版本把**亮度高**的像素映射到密集字符，结果白底网页变成一整片 `@`、
文字反而变成稀疏空格，页面完全不可读。

**2. 两条 ramp 的索引方向必须相同。**
早期 `RAMP_DARK_TEXT` 是「空→密」而 `RAMP_LIGHT_TEXT` 是「密→空」，
但索引公式只有一套，于是暗色页面（Bing）命中 `ink≈0` → 取到 ramp 第 0 位
→ 整屏 `@`。现在两条共用一个升序 ramp，方向差异由 `ink` 计算承担。

**3. 底色判定要用「全图众数色亮度」，不能用平均亮度。**
`bgLuma` 取所有格子「格内众数色亮度」的**峰值**（量化补偿 +8）。
背景格数量远多于文字格，峰值必然落在背景上。知乎登录页整图平均 210
而真实底色是纯白 240；若用平均值判定会低估，进而把 `lightText` 判错。
峰值占比低于 5%（照片/复杂图，无明确底色）时退回平均亮度。

**4. 墨量 = 相对底色偏离（dev） + 格内极差（spread）。**
```js
const delta = lightText ? bgLuma - localL : localL - bgLuma
const dev   = Math.max(0, delta) / 255
const spread= Math.max(0, s.maxL - s.minL) / 255
let ink = dev * 3.4 + spread * 1.75
if (ink < 0.05) ink = 0                    // 纯背景归零，避免噪点
ink = (ink - 0.10) * contrast + 0.02
```
两个信号缺一不可：4×8 的格子会把笔画平均掉，一格里 25% 是深色文字时
均值只偏离底色一点点，**只看 dev 的话正文永远停在中等墨量、标题和正文分不出来**；
`spread` 恰好对「一半底一半字」的格子最敏感。反过来纯背景格两者同时归零，
页面才干净。早期版本把 `spread` 乘了 `(1 - flatness)` 抑制项，
正好把最重要的信号压掉了，导致最重字符只到 `A`、全页灰蒙蒙一片。

## 已知限制

- **超长页面在约 44 万像素处截断（≈440 屏）**。这是防御无限滚动 feed 把
  提取拖死的硬上界；真被截断时页面会印一行「── 页面过长，此位置以下约
  N 个区块未加载 ──」，不会无声消失。
- **`e` 展开出来的折叠正文是纯文本，里面的链接点不了**。要连链接一起用，
  改按 `E`（真展开页面）—— 展开后这些链接就是普通可见元素，`v` 元素清单里能选中点击。
- **折叠探测可能把「站点为窄视口藏起来的导航菜单」也算进去**。实测 Bing 的隐藏导航
  99 字、MDN 的侧边栏导航 1790 字都会被登记。所以默认**不自动展开**，
  它们只占一行标记 —— 展开与否交给用户判断。
- **靠请求注入的内容 `e` 拿不到**。「加载更多评论 / 下一页」这类点了才发 HTTP 的，
  折叠正文压根不在 DOM 里，只能按 `E` 真实点击后再重新提取。
- **鼠标点击只在文字模式下有效**（滚轮两种模式都能用）。图片模式是像素网格，
  没有「这一格属于哪个 DOM 块」的信息，按像素反推页面坐标去点很容易误触。
- **鼠标上报会接管终端的拖选**。想拖选复制文字：按住 `Shift`（xterm 系通用约定），
  或 `: /mouse` 关掉上报，或用 `--no-mouse` 启动。
- **站点用 JS 主动开窗（`window.open()`）的标签页仍不会被收编**。走 `<a target=_blank>`
  的已经掰成本标签打开了（占绝大多数），但 JS 弹出的新窗口仍开在后台 ——
  要收编它需要监听 `Target.targetCreated` 并把新 target 接成标签页，尚未实现。
- **点纯文字段落不会有任何动作**，只给一句提示。文字模式是重排过的，
  终端列与页面 x 之间没有线性对应关系，猜着点比不点更糟。
- **`E` 会真的动页面**，属于有副作用操作。已做防护（跳过表单内控件、
  `type=submit` 按钮、带真实 `href` 的链接，单次最多点 12 个），
  但仍建议只在确认无害的页面上用。
- **二维码能扫，但只在文字模式下**。文字模式走「无损直读」，画出来的码可以真扫
  （见上面「二维码」一节）。切到图片模式（`m`）后二维码会重新变成字符画，
  那就只能"看出这里有个码"，扫不了。
- **二维码识别依赖足够的分辨率**。元素在页面上小于约 88px、
  或截图后每模块不足 1.2 像素时无法还原矩阵，会静默退回字符画。
- **超时后会渲染"不完整"的页面**，这是**有意的**。等满超时会显示已加载的部分并写明
  「加载超时，显示的是已加载部分（r 重试）」。冻结的界面比不完整的页面糟糕得多 ——
  见上面「不会卡住：加载等待策略」。
- **图多的页面只抓前 24 张**（可用 `EDGE_TUI_MAX_SHOTS` 调）。被跳过的地方会写
  「未抓取（超出本次抓图预算）」，二维码永远优先抓。
- **弹窗会被自动确认**（`alert`/`confirm` 一律接受）。文字浏览器里没有弹窗交互，
  不自动关掉会**永久冻死渲染进程**。次数会写在状态栏。
- **纯文字模式下无法看到整体版式**。想看版式按 `m` 切到图片模式。
- **表单控件只在文字模式下可见**。图片模式（`m`）看到的是像素，控件行那套
  `▢ 搜索框…` 标记不适用；输入也仍然可用（按 `i` 走的是同一条 `focusField` 链路）。
- **页面控件很多时只取前 80 个**（病态筛选器页面有几百个字段）。
- **JS 里用 `type="search"` 之外的隐式搜索框认不出来**。判据是 `type` / `name` /
  `role=search` / 表单 `action` 这几个特征；纯 `div` + 自定义 JS 拼出来的搜索框
  只能靠 `Tab` 或 `v` 元素清单去点。
- **中文输入优先用 `Ctrl+V` 粘贴**。终端会把整段 UTF-8 直接交给我们（括号粘贴，
  一次粘贴一个整体事件），绕开 IME 组合过程；实测 `insertText` 收中文本身没问题
  （`tests/test-field.mjs` 里 `insertText("必应测试")` 就是通的），
  真正的短板在终端那一侧 —— 见下一条。
- **Windows 传统控制台（conhost）里的 IME 常常打不出字**。那是 conhost 与
  原始模式（raw mode）不对付，程序侧看不出区别；启动时会明确提示。
  想用输入法打中文请换 Windows Terminal。想知道终端到底送来了什么，
  设 `EDGE_TUI_KEYS=1` 后看 `crash.log` 里的 `[keys]` 行。
- **站点自绘的输入控件可能连 DOM 注入都不吃**（框架拦截了 `input` 事件）。
  这种情况状态栏会明说「该控件拒绝输入」，只能改用 `v` 元素清单或 `o` 地址栏。
- **部分站点对 headless 有降级**。必应会在 headless 下返回精简版首页（无导航、
  无背景图），不是渲染管线的问题。需要完整版可考虑加 `--user-agent` 伪装。
- **多标签页最多 12 个**。每个标签页是一个真实的 Chromium 页面，
  会各占一份渲染进程与一份内存里的排版结果（长文档页面尤其明显）。
  标签页之间的切换是纯内存操作，但**后台标签页不会自动降载**（不释放截图与排版）。
- **多标签页不跨进程共享登录态以外的东西**：书签与历史仍是全局的（共用一份 JSON）。
- **纯文本终端不支持 24-bit 色**时会退化成近似色。建议 Windows Terminal、
  WezTerm、iTerm2 等现代终端。
- **`run.mjs` 需要真实 TTY**。stdin 是管道时 `setRawMode` 不可用，
  无法用脚本模拟按键驱动交互模式；交互逻辑通过直接调用底层 CDP 能力来测
  （见 `tests/test-picker-logic.mjs`）。

## 开发

```bash
node tests/run-all.mjs             # 一次跑完所有套件（推荐，避免子进程被信号组杀掉）
node tests/run-all.mjs --no-live   # 只跑不依赖真实站点的套件
node tests/run-all.mjs --force-live test-zhihu-fix   # 无视环境探测强行跑
```

### 环境闸门：被站点拦截 ≠ 代码回归

有 8 个套件依赖真实站点（知乎 / 必应）。这些站点会对同一出口 IP 的**高频自动化访问**
返回拦截页 —— 知乎给的是「安全验证 · 系统监测到您的网络环境存在异常」，
页面只剩 6 个块、0 个媒体、0 个控件，于是断言全灭。

实测过这一幕：14 分钟前同一份代码 17 套件全绿，14 分钟后 7 个套件飘红，
原因只是把自己跑限流了。**误报的测试套件比没有测试更糟** ——
一旦「跑出来是红的」成为常态，真正红了的那次也没人看。

所以 `run-all.mjs` 在开跑前先探一次活口（知乎看 URL 是否跳到 `/account/unhuman`、
标题是否含「安全验证」、正文长度、二维码 canvas 是否存在）：

```
环境探测（真实站点可达性）：
  ⊘ zhihu     被拦截：安全验证 - 知乎
  ✓ bing      可达

⊘ test-zhihu-fix  回归  跳过（zhihu 被拦截：安全验证 - 知乎）
...
── 7 个套件 · 7 通过 · 0 失败 · 10 跳过
── 跳过套件（环境受限，不是回归，别当红看）
```

跳过的套件**不算失败**，退出码为 0，并在汇总里逐条写明原因 —— 不含糊、
不静默、也不冒充成功。`--force-live` 强制跑，`--no-live` 直接全部跳过（离线开发用）。

### 看「终端里到底长什么样」

```bash
node run.mjs https://example.com --dump > dump.bin
node tests/replay-dump.mjs dump.bin      # 还原成不含 ANSI 的纯文本画面
```

`replay-dump.mjs` 是个小型终端模拟器：处理 `\x1b[row;1H` 光标定位、
`\x1b[K` 清行、CJK 双宽字符，最后按行列打印。排查「终端里看到什么」
这是最直接的手段 —— 比盯着 ANSI 字节流猜快得多。

### 排查「输入类」问题的顺序

1. **终端到底送来了什么？** `set EDGE_TUI_KEYS=1` → 看 `crash.log` 的 `[keys]` 行。
   这一步能区分「终端根本没发字节」（IME/终端问题）和「我们收到了但没处理对」（解码问题）。
2. **页面侧到底吃没吃？** 看状态栏有没有「已自动重新聚焦 / 已改用 DOM 输入」，
   以及 `crash.log` 里的 `[input] … 走了兜底路径`。
3. **搬回本地复现**：`node tests/probe-node-swap.mjs`（换节点 → 静默失效的复现），
   `node tests/probe-search-flow.mjs`（整条搜索旅程）。
